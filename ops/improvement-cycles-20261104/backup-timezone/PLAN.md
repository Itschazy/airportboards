# Запуск 2/20: восстановление JSON и часовой пояс

База b18777a9; воспроизведение: Date=2026-11-03T02:00:00Z,
Asia/Tokyo → write(HND–LAX, 2026-11-03) → backup → America/Los_Angeles
→ parse. Старый код бросает m143; сохранённый журнал при этом читается нормально.

Гипотезы в порядке проверки:
1. Строгий parse сравнивает сохранённую дату с локальным сегодня — подтверждено.
2. Одного исправления parse мало: write заново отвергает новую для устройства
   запись с такой датой — подтверждено отдельной проверкой writeAsync.
3. Undo повторяет запрет текущей даты, хотя только удаляет уже принятые записи —
   подтверждено чтением активного пути и тестом импорта/отмены со сменой TZ.

Решение: отдельные parseBackup/restoreAsync. Схема, ID, аэропорты, календарь,
размер и лимит записей проверяются; дата backup не сравнивается с текущими часами.
exportedAt не является доверенным доказательством. Это намеренно допускает любую
корректную календарную дату из JSON, даже будущую при текущих часах; ввод и CSV
остаются строгими. Устойчивое восстановление важнее повторного определения
историчности даты. Restore сливает свежий журнал под общей блокировкой.

Дополнительная находка в реальном UI: пустое состояние скрывает backup-entry,
поэтому на новом устройстве нельзя добраться до JSON без фиктивного перелёта.

12 языков, без изменения первого экрана/CSS. Проверить настоящий file chooser,
превью, сохранение, reload, повтор и закрытие на 375px.
